# java-blackjack

## 블랙잭 사전 학습 📖

### 실험1: main 기반 검증의 한계

#### 관찰 기록

- 케이스를 3개에서 6개로 늘릴 때 main 메서드 안에 println 라인을 3줄 더 추가해야 했다. 케이스마다 기대값도 직접 계산해서 == 16, == 20 등을 손으로 써야 했다. 추가하는 것 자체는 어렵지
  않지만, main 메서드가 점점 길어지면서 어떤 줄이 어떤 상황을 테스트하는지 주석 없이는 파악하기 어려워졌다.
- calculateSum 내부의 A 처리 로직을 수정했을 때, 실행 결과가 true true false true true true로 나왔는데 세 번째 false가 어떤 케이스인지 바로 알 수 없었다. 실패한
  케이스를 찾으려면 코드의 세 번째 줄을 직접 찾아야 했고, 기대값이 뭐였는지도 코드를 다시 읽어야 알 수 있었다.
- 로직 수정 후 main을 다시 실행해서 6개 줄이 전부 true인지 눈으로 확인했다. 케이스가 늘어날수록 몇 번째 줄이 어떤 케이스인지 헷갈리고, 로직을 수정했을 때 이전 케이스가 여전히 통과하는지 전부 눈으로
  다시 확인해야 했다.

### 실험2: 테스트 코드 작성

#### 관찰 기록

- 테스트의 내용을 메서드명(A_두_장과_K와_4에서_합이_21을_넘으므로...)으로 만들었기 때문에 코드를 읽지 않아도 어떤 것을 테스트하는지 파악하기 쉽다.
- 현재 calculateSum은 순수 계산이라 어려운 부분이 없었다. 다만 만약 카드를 List<String>이 아니라 Scanner 혹은 랜덤으로 입력받는 구조였다면, 테스트할 때마다 입력을 Fake 객체로
  변환해야해서(협력 객체의 고립을 위해서) 테스트 작성이 어려워진다.
- 현재 카드가 String이라서 "A", "K", "5" 등을 메서드 안에서 if-else로 분기하고 있다. 숫자와 문자(A, K, Q, J)를 하나의 카드 객체 및 일급 컬렉션으로 만들어서 스스로 자신의 점수를
  알려주는 구조로 바꾸고 싶다.

### 테스트 단위에 대한 내 의견

- 테스트(단위 테스트)는 입력과 출력이 명확한 순수 계산 로직에 가장 효과적이다.

### 반드시 테스트할 것

- A의 1/11 변환처럼 조건에 따라 결과가 달라지는 부분이 많아지면 경우의 수가 여러 개라 사람이 머리로 다 추적하기 어렵기에 가능하면 다양한 테스트 케이스를 만들어서 테스트해야한다.

### 테스트하지 않을 것

- System.out.println으로 결과를 출력하는 부분은 테스트하지 않을 것이다. 테스트하려면 출력 스트림을 가로채야 하는 부분이 생긴다.
